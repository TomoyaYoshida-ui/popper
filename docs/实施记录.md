## C7 验证项 3 判结：`--sandbox` 端到端在真实 Linux 上跑通（2026-09-18，首跑红 78 → 当日修复 → 第二跑全绿）

- **要闭的洞**：上面的 ubuntu job 只跑单测——它能证明「某条断言在 bwrap 下成立」，证明不了从 `init` → `search --sandbox` → `freeze` → `confirm --sandbox` → `report`/`replay` 的**整条生命周期**里候选进程始终在被约束状态下执行，而 README/技术方案 M2 承诺的正是后者。这条一直挂在「明确未完成」。
- **取证工程选择**：`examples/ode-convergence`（纯标准库、3 seeds、budget=2、候选 midpoint/rk4、基线 euler）。选它是因为它带**数学真值锚点**：三种显式单步法的观测收敛阶已知为 1/2/4，于是「沙箱把执行挡坏了却仍然绿」这类假通过会被数值拦下——只要求「跑完不报错」的端到端，是可以全程什么都不做也绿的。
- **三层彼此独立的证据**（`.github/scripts/e2e_sandbox_experiment.py`）：① **候选现场自述**——见证代码在 `init` **之前**注入候选 `model.py`，因此属于已注册代码（哈希被 init 记账、执行前后各校验一次），没有「跑完再改代码伪造证据」的空间；观察行打到 stderr，落进 run 目录并进入该 run 的产物 manifest ⇒ 见证本身在证据链里。② **宿主侧独立复核**——作用域外两处 canary 由驱动在宿主上直接查存在性，候选说谎也躲不过。③ **科学正确性**——实测阶对已知真值。
- **正向对照不是可选项**：见证先断言「作用域内必须写得动」（`scope_write=GRANTED`）。缺了它，两条越界写 `DENIED` 可能只是「什么都写不了」造成的假通过（Windows 误标整盘只读、Linux 漏挂 `--bind` 都会这样）。
- **断言分两档，避免拿平台差异造假红**：两平台都主张的（写作用域、命令拦截、保留集封读、trust 字段、证据链）一律硬断言；只有某平台主张的（空 netns、namespace 内 pid、沙箱内可观察 rlimit）只在 `popper.sandbox` 能力探针真主张时才判红。封读窗口同样按设计只覆盖 test 划分——dev 划分可读是已登记边界，观察值全部进摘要表格但不判红。
- **本机实跑（Windows/低完整性后端）EXIT=0**：5 run（dev 3 + test 2）× 3 重复，实测阶 1.0295/2.0518/4.0565 与 1.0350/4.0670 对真值 1/2/4；越界写全 `DENIED`、命令拦截 `DENIED:PermissionError`、test 划分保留集 `BLOCKED:PermissionError`、dev 划分 `READABLE`。
- **端到端第一次真跑就拦出两处产品侧假陈述**（都是单测层看不见的，因为它们是「跨产物的口径」）：① `popper/isolation.py` 的 `backend` 字段用的是 `selected_backend_name()`（内部模块名 `win_lowil`/`linux_bwrap`），与 C7.1 已立的「回执必须用稳定名」矛盾——那份报告是对外递安全边界用的凭据，把 bubblewrap 签成 `win_lowil` 等于让它自称 Windows 低完整性；改用 `execution_backend_name()`。② `popper/core.py` 的 `report()` 把「执行模式」行**写死**为「可信本地代码；……尚未提供容器安全隔离」——一个用 `--sandbox` 跑完的项目会在**交付产物里**自称没隔离，与同目录 `results.json` 的 `trust` 直接矛盾。新增 `execution_mode_line(results)` 按实际 run 的 trust 字段实算；刻意**不**从当前平台反推后端名（后端名不存在每条 run 里，拿今天的探活描述昨天的执行又是一次漂移）。
- **驱动自己写坏的两处（自查抓出，代价为零，比 CI 上抓出便宜）**：① `WITNESS_SNIPPET` 里误引用驱动模块常量 `BLOCKED_PREFIX`——注入代码跑在**候选进程**里拿不到它，真跑必 `NameError`，改为字面量并加一条门禁双向钉住「snippet 只能自包含」。② 后端不可用的判红从「跑完再判」改为 preflight 直接 `return 2`（没有后端的端到端就是假端到端，与单测侧 `POPPER_REQUIRE_SANDBOX=1` 同一取向）。
- **`command_block` 的假绿口子（本机全绿之后复查出来的，不是跑出来的）**：旧判据接受任何 `DENIED`，而 sitecustomize 的 `_check` 在 OS 查找二进制**之前**就抛 `PermissionError`——所以 ubuntu runner 上若没装 curl，`DENIED:FileNotFoundError` 恰恰意味着拦截层没参与，却会被计成「已拦截」。收紧为只接受 `DENIED:PermissionError`。这类「只会在该抓的东西上变绿」的判据，是端到端仪表最典型的失效方式。
- **CI 接线**：新增 `linux-sandbox-e2e` job。① **必须独立成 job**：annotation 预算是**每个 check run 最近 10 条**，两套仪表挤进同一个 job 会互相顶掉（skip 名单顶掉端到端结论，或反之）；拆开后各有 10 条且并行跑、不多花墙钟。② 环境准备抽成 `.github/actions/sandbox-env`（装 bwrap / AppArmor userns 例外 / 真实形状探活，全部 `continue-on-error`），两个 ubuntu job 共用一个出处——两份抄本迟早漂成「一个 job 修了、另一个还绿着」。③ 退出码落盘 + `if: always()` 的「端到端仪表不得沉默」兜底步（脚本在能递出结论之前就崩掉时，也要把退出码、字节数、tail 递出来）。
- **本轮被门禁反过来咬到的三处（每一次都是门禁在起作用，不是门禁的锅）**：① 把环境步骤抽进 composite action 后，`test_the_isolation_check_itself_bites` 因在 job 块里找不到「安装 bubblewrap」而红——修法不是删门禁，而是新增 `expand_local_actions()` 把本地 action 就地展开喂给既有扫描。② 那个展开函数自己错两次，都被反向验证逮住：缩进偏移写成 +4（正确是归一化后递到 6 空格，否则 `STEP` 正则一个步骤也看不见，两条「环境步骤不得当门禁」当场变**假绿**），以及 `- uses:` 正则只匹配内联写法、不匹配本仓库「先 `- name:` 再另起一行 `uses:`」的写法（于是展开静默成为空操作）。现在既有展开生效断言、也有反向断言（把 `always()` 换掉必须被识别成沉默仪表）。③ `test_the_reporter_runs_on_green_jobs_too` 用全局计数 `count(ci_failure_summary.py) == count(if: always())` 当判据，我新增的第二套仪表也是 `always()` 上报步骤却不调该 helper，3 != 4 当场红——改成**按步骤**判（哪个步骤调了 helper，它自己就得有 `always()`），既保住牙口也不惩罚新增仪表。

## Actions 第七跑：补上 skip 名单上报通道——仪表从此在绿跑上也开口（2026-09-18）

- **要闭的洞**（第六跑自己记下的）：仪表只挂在 `if: failure()` 上，job 绿时整步不执行；而带原因的 skip 在外部与「真跑了」完全不可区分——于是「`POPPER_REQUIRE_SANDBOX=1` 下那 5 项真实沙箱用例到底跑了没」与「集合字体渲染用例是跑是跳」永远读不出来。只报失败的仪表，等于在自己最该看的分支上沉默。
- **结构改动三处（每个 job 一致，共 3 个测试步骤 + 3 个上报步骤）**：① 测试命令 `-rfE` → `-rfEs`（不带 `-rs` 就没有 `SKIPPED [N] 位置: 原因` 这些行，名单从源头不落盘）；② 测试步骤加 `id: pytest`，上报步骤改 `if: always()` 并注入 `TEST_STEP_OUTCOME: ${{ steps.pytest.outcome }}`；③ helper 新增 skip 解析（当时为 `skip_entries`/`skip_total`/`declared_skips`/`skip_signatures`/`skip_notice`/`skip_markdown`，其中 `skip_signatures` 已在下一提交重命名为 `skip_clustered`，因为 notice 与摘要要用同一份聚合结果）与绿跑分支（`emit_green`）。`SKIPPED` 行的格式先在 `.pytest_cache/scratch/` 用四种 skip 写法（`skipUnless`/`skipIf`/`skipif` mark/运行时 `pytest.skip`）实测得到，不凭记忆写正则。
- **`TEST_STEP_OUTCOME` 不是可选装饰，是这轮改动的前提**：上一轮刚把「无失败行也必须开口」钉成契约（run `35303020780` 的教训），而绿跑天然没有失败行——直接把 `if: failure()` 换成 `always()` 会让每个绿 job 都收到一条「崩在采集前」的假 error。所以判据必须先给：`outcome=success` 走「只报 skip、绝不发 error」，其余（failure/skipped/空）走原分支。反向验证实测到这一层：同一份绿跑输入，HEAD 版发 `::error::no FAILED/ERROR/SUBFAILED/SUBERROR line but pytest exited 0`（误导），新版 0 error + 1 notice。
- **两个刻意的取舍**：① 绿跑用 `::notice::` 而不是 `::error::`（无事不报是原契约，但沉默不是——skip 名单就是绿跑的正文）；notice 排在失败项**之前**打印，GitHub 只留最近 10 条，红跑时被顶掉的应当是 skip 而不是失败详情。② 「汇总行写着 N skipped、短汇总里却没有 `SKIPPED` 行」判为**仪表坏了**（有人把 `-rs` 改掉了），发 `::warning::`：不能发 error（job 确实绿），也不能沉默（那正是本轮要修的形状）。
- **顺带修掉一处会让名单变成问号的编码坑**：pytest 的 skip 原因与断言消息都是中文，而它重定向到 `pytest-output.txt` 时按宿主 locale 编码（中文 Windows 为 cp936）。这与 `verify_claims.py` 踩过的是同一个坑，解法也一致：测试步骤 `env: PYTHONIOENCODING: utf-8`。
- **门禁**：`tests/test_ci_reporting.py` 新增 8 条用例（行为 5：绿跑递名单且不发 error、少了 `-rs` 要吱声、outcome=success 与失败行/非零退出码互斥【2 subTests】、红跑的 skip 名单不得丢、`SKIPPED` 不得被计成失败；ci.yml 契约 3：上报步骤必须是 `always()` 且仓库内不再残留 `if: failure()`、每处调用都要拿到 outcome、每条 pytest 命令都要带 `-rfEs`）。【本条初稿误写为「7 条行为 + 17 passed」，已按 `git show` 逐提交核用例名修正：该文件在 `a43f143` 为 15 passed（旧 7 + 新 8）。】

## C7.1 Linux bubblewrap 后端的可执行性回炉 + 跨平台口径修正（2026-09-17）

- **背景**：下面 C7 章节的 Linux 后端从提交到现在**一次也没在 Linux 上真正执行过**（开发机为 Windows，新增的 Linux 用例全部 skip）。复核发现多个会在 Linux CI 上直接暴露的缺陷，以及跨平台后仍残留大量「只有 Windows」的假陈述。本条目是对 C7 的回炉，不是新增能力。
- **探活从「版本号」改为「真跑一次沙箱」**（`linux_bwrap._run_probe` / `_PROBE_ARGV` / `APPARMOR_HINT`）：原 `available()` 用 `bwrap --version` 退出码判断。Ubuntu 23.10+/24.04+ 默认由 AppArmor 的 `kernel.apparmor_restrict_unprivileged_userns` 拒绝非特权用户命名空间，此时 bwrap **已安装且 `--version` 返回 0**，但任何真实沙箱都建不起来——硬门禁与 `--sandbox` 会建在假前提上。现在探活用与 launch 同形状的最小沙箱（`--unshare-all --ro-bind / / --dev /dev --proc /proc --tmpfs /tmp` + 当前解释器），并缓存失败详情；`_require_bwrap()` 不可用时抛 `OSError` 带真实原因与修复指引，绝不静降级。
- **修掉命令拦截被静默遮蔽**：`--tmpfs /tmp` 遮住宿主 /tmp，而 `sitecustomize` shim 目录就建在 `tempfile.gettempdir()` 下——不重新挂回，拦截就「看起来在用、其实没约束」。`launch_bwrap` 现在把 `POPPER_SANDBOX_SHIMDIR` 作为 `ro_paths` 在 `--tmpfs /tmp` **之后**显式 `--ro-bind`，并把该挂载归入 `_build_bwrap_argv` 的固定层次。
- **修掉禁读屏蔽不可用**：原来只追加 `--ro-bind /dev/null <path>`，在只读根上不会凭空造出文件挂载点（C7 新增的 Linux 用例在 CI 必失败）。现在先对每个禁读路径的**父目录**做只读挂载，再将 `/dev/null` 遮蔽放在最后叠（路径最深，一定盖在读写视图之上）；scope 的 `--bind` 排在父目录只读挂载之后，避免「禁读文件正好在工作区内」时把整个工作区留在只读视图。`seal_read` 对不存在的路径改为显式 `OSError`（登记不存在路径等于「以为封了读」）。
- **路径与限额语义**：所有 mount 参数经 `_abs()` 绝对化（namespace 内没有「相对宿主 cwd」的概念）；`RLIMIT_NPROC` 按**真实 UID** 计数而非按进程树，直接写声明值会把用户已有进程算进去、候选连一个子进程都起不来，改为 `_nproc_ceiling()` = 「宿主上本 UID 当前进程数 + 声明值」（读不到时 +512 保守余量），能力清单里如实标为 fork 炸弹兜底而不是 Job Object 式按作业精确计数；整树终止复用 `base.force_kill_tree`（bwrap 是新 pid namespace 的 1 号，杀它即内核回收整树）并补 `--die-with-parent`。
- **能力声明按后端下发**：`base.SandboxBackend` 新增 `capability_notes()`，`win_lowil.CAPABILITY_NOTES`（8 条）与 `linux_bwrap.CAPABILITY_NOTES`（8 条）各自提供平台相关条目的机制描述，`popper/isolation.py` 改为「平台中立默认 + 后端覆盖」合并，报告新增 `backend` 字段（12 条目数不变，`isolation_items=12` 门禁仍成立）。代理拦截环境变量抽成平台中立的 `base.proxy_block_env()`，两个后端共用。
- **回执与报错文案不再写死 Windows**：`sandbox/__init__.py` 新增 `_RECEIPT_BACKEND_NAMES`（`win_lowil` → `windows_low_integrity`、`linux_bwrap` → `linux_bubblewrap`）、`execution_backend_name()`、`selected_backend_name()` 与单一事实源 `no_backend_message()`（Linux 上附探活详情与 AppArmor 指引）；`workers/local.py` 的 `WorkerReceipt.execution_backend` 改为实算（不能把 bwrap 签成 Low IL），`confirmation_runner.py` 改按 `SANDBOXED_RECEIPT_BACKENDS` 成员判定，`core.py` / `controller.py` / `confirmation_cli.py` 的无后端报错统一走 `no_backend_message()`。
- **测试**（新增 18 个用例，其中 16 个 Linux 后端相关均可在本机跑）：`LinuxBubblewrapArgvConstructionTests` 锁定挂载叠放顺序（shim 在 `--tmpfs /tmp` 之后、父目录先于 `/dev/null` 遮蔽、scope 在父目录只读之后、遮蔽最末、均在 `--` 之前）、路径绝对化、封不存在路径报错、`_nproc_ceiling` 换算；`LinuxBubblewrapProbeTests` 验证探活形状（不含 `--version`）、未安装/命名空间被拒两种失败路径与 AppArmor 指引、结果缓存；`LinuxBubblewrapLaunchTests` 以假 `Popen` 验证 launch 的 argv 组装、限额经 env 透传、代理拦截、`start_new_session`，以及「探活失败就不启动」。为此把 Linux 后端的平台闸门收拢为 `_is_linux_platform()`（只 patch 闸门，不改全局 `os.name`，否则 pathlib/tempfile 行为失真、测到的不是真实代码路径）；`_require_backend_in_ci()` 使 `POPPER_REQUIRE_SANDBOX=1` 下「后端不可用」从 skip 变 fail。另两个给后端契约：`test_execution_backend_names_are_stable_and_distinct`（两个后端签不同名，无后端为 None）与 `test_no_backend_message_names_both_registered_backends`（报错文案同时点名两个后端、保留 `--trusted-local` 出口、且旧的「只有 Windows」描述不得回归）。
- **CI 硬门禁真实化**（`.github/workflows/ci.yml` linux job）：显式 `apt-get install -y bubblewrap`；检测到 `kernel.apparmor_restrict_unprivileged_userns` 为 1 时写 `/etc/apparmor.d/bwrap` 的 profile 级 `userns` 例外并 `apparmor_parser -r`（比全局 `sysctl=0` 弱影响面，无 `apparmor_parser` 时才退回）；新增「真建一次命名空间」的探活步骤（失败即报出原因）；job 级 `POPPER_REQUIRE_SANDBOX=1`。【2026-09-18 修订：环境准备/诊断类步骤已改 `continue-on-error: true`——「失败即红」会让 GitHub 把后面的全量测试整步 skip，反而遮掉主信号，见文首那节；门禁由测试本身与 `POPPER_REQUIRE_SANDBOX=1` 承担。】
- **文档**：`README.md`、`docs/技术方案.md`（§2.2 隔离层与§8）改为两个后端并列描述，并补上「可用性由探活得出、不是装了就算」；`base.py` 中「Linux bubblewrap 尚未实现」的过期注释、`win_lowil.py` 中「当前唯一实现」等假陈述同步清除。

## C7 Linux bubblewrap 沙箱后端：跨平台隔离层补齐 Linux 半边（2026-09-17）

> 本节是当时的执行快照；其中「`available()` 用 `bwrap --version`」、「`--ro-bind /dev/null <path>` 直接追加即可」等描述已被上方 C7.1 修订，以 C7.1 为准。

- **背景**：`popper/sandbox/__init__.py` 的注册表此前只登记 `win_lowil.BACKEND` 一项。`base.SandboxBackend` 协议注释明示「macOS seatbelt 与 Linux bubblewrap 尚未实现，故未注册」。后果：非 Windows 上 `selected_backend()` 返回 `None` → `--sandbox` 显式报错指向 `--trusted-local`；`.github/workflows/ci.yml` 的 Linux job 标 `continue-on-error: true`（信息性，不阻断合并）；§0.1 M2 的跨平台交付承诺只完成 Windows 半边。
- **`popper/sandbox/linux_bwrap.py` 新建**：镜像 `win_lowil.py` 的薄适配结构（模块级函数 + 末尾 `BACKEND = LinuxBubblewrapBackend()`）。核心实现：
  - `available()`：`bwrap --version` 退出码 0 + Linux 平台，结果缓存。无 bwrap 时返回 False，`--sandbox` 显式报错指向 `--trusted-local`（与无后端语义一致，不静默降级）。
  - `label_write_scope(path)` / `unlabel_write_scope(path)`：no-op（仅把 path 加入 `_SCOPE_PATHS` 集合，供 launch 构造 `--bind`）。与 Windows `icacls /setintegritylevel Low` 不同，Linux 无对应内核标签语义，scope 仅作为 mount namespace 内的 rw 挂载点。
  - `seal_read(path)` / `unseal_read(path)`：把 path 加入/移出进程级 `_SEALED_PATHS` 集合。这是 **per-launch 的状态记录**，不是内核级 toggle——bubblewrap 的 mount namespace 在 launch 时固定，无法运行时改。
  - `launch_bwrap(...)`：构造 bwrap argv = `--unshare-all`（新 mount/pid/ipc/uts/net/user namespace）+ `--ro-bind / /`（host root 只读）+ `--bind <scope> <scope>`（运行工作区 rw）+ `--dev /dev` + `--proc /proc` + `--tmpfs /tmp`；对 `_SEALED_PATHS` 中每个 path 追加 `--ro-bind /dev/null <path>` 屏蔽（候选读到 EOF / 空字符串，内核强制、无法绕过读到真实数据）。资源限额经 bootstrap 脚本在沙箱内 Python 入口运行前 `resource.setrlimit(RLIMIT_AS / RLIMIT_CPU / RLIMIT_NPROC)` 设置（与 Windows BOOTSTRAP 同思路；preexec 作用在 Popen 启动的 bwrap 进程上，不影响沙箱内 python，故限额必须在 bootstrap 里）。整树终止：`start_new_session=True` 创建新会话，超时/非零退出 `os.killpg(SIGKILL)`。命令拦截：复用 `win_lowil.SITECUSTOMIZE`（与平台无关，纯 Python 层，可绕过，如实标注）。
- **平台差异的诚实标注**：Windows 候选读保留集得 `PermissionError`（MIC 强制标签 NO_READ_UP）；Linux 候选读保留集得空字符串（`/dev/null` 屏蔽）。两者都是「内核强制、候选无法读出真实数据」，文档与测试代码注释如实标注该差异，不强行在 Linux 复现 PermissionError（那需要 chmod 或换 UID 运行，会污染宿主文件权限或大幅增加复杂度，与「如实标注边界」原则相悖）。
- **`popper/sandbox/__init__.py` 注册**：`_BACKENDS` 元组追加 `linux_bwrap.BACKEND`（顺序即选择优先级，Windows 在前 Linux 在后；`selected_backend()` 按序找第一个 `available()` 为真的后端）。模块 docstring 与 `_require_backend()` 错误信息同步更新为「已登记 win_lowil 与 linux_bwrap；后者需安装 bwrap；macOS seatbelt 尚未实现」。
- **测试**：`tests/test_sandbox.py` 顶部加 `_is_linux()` + `_backend_available_on_this_platform()` 两个助手，让原本硬编码 `os.name == "nt"` 的断言改为平台条件分支：
  - `test_available_matches_platform` / `test_seal_read_available_matches_platform`：Windows 总真；Linux 看 bwrap；其它平台假。
  - `test_write_scope_label_rejects_non_windows` → `test_write_scope_label_rejects_unsupported_platform`：跳过 Windows 与 Linux-with-bwrap，只对无后端平台断言 OSError（原版本在 Windows 上是空函数体通过的「假阳性」，现在改为显式 skipTest）。
  - `test_seal_read_rejects_non_windows` → `test_seal_read_rejects_unsupported_platform`：同上。
  - `test_registry_entries_satisfy_the_protocol`：断言注册表同时含 `win_lowil.BACKEND` 与 `linux_bwrap.BACKEND`，且都满足 `base.SandboxBackend` 协议。
  - `test_selected_backend_matches_availability`：Windows 断言 `win_lowil`；Linux+bwrap 断言 `linux_bwrap`；其它 None。
  - 新增 `LinuxBubblewrapReadSealEnforcementTests`（`@skipUnless(_is_linux() and sandbox.available(), ...)`）：与 Windows `ReadSealEnforcementTests` 平行结构，断言候选读 sealed 文件得空字符串（`res.get("read", "") == ""`），用户在窗口内仍能读，窗口结束后沙箱重新可读真实内容。
- **CI 升为硬门禁**：`.github/workflows/ci.yml` 的 Linux job 去掉 `continue-on-error: true`，重命名为「pytest / ubuntu / bubblewrap 沙箱后端」。ubuntu-latest 默认装 bwrap，因此 Linux 上 `sandbox.available()` 为真，沙箱相关测试会真正跑（不再 skip）。本地 Linux 无 bwrap 时 available() 返回 False，`--sandbox` 显式报错。
- **回归**：Windows 上 584 passed / 4 skipped / 305 subtests passed（之前 586/1/305）。差异：2 个空函数体「假阳性」改为显式 skipTest（计入 skip 不计 pass），1 个新增 Linux-only 测试在 Windows skip。无真实失败。Linux CI 跑时会执行新增的 `LinuxBubblewrapReadSealEnforcementTests`。
- **边界**：`linux_bwrap` 的 `seal_read` 是 per-launch 状态记录而非内核级 toggle，仅在 `sealed_reads` 上下文管理器包裹 `launch` 的用法下成立（这也是 controller 唯一用法）；脱离该用法单独调用 `seal_read` 不会有任何效果，与 Windows 的「标签 ACE 立即生效」不同，代码注释已明示。需要更强 MAC 保证的场景应使用外部评估服务（`external_confirmation`）。

## C1 holdout 隔离：生成代码 revision 候选可经 Worker 在 test split 上确认（2026-09-17）

- **背景**：C2 合并两条受限执行路径后，`controller.confirm()` 在所选候选的 dev observation 来自生成代码 `CodeRevision` 时，会抛 `ProtocolError "请接入隔离 holdout worker 后确认"`（原 914-921 行硬阻塞）。根因：`Experiment.confirm` 用 `self.evaluate(config, "test", ...)` 跑**项目原始注册代码**，对 revision-based 候选而言「测试结果」对应的代码与「dev 阶段冻结的候选」不一致，等于冒名顶替。
- **`popper/core.py` 拆 `Experiment.confirm`**：原单一方法拆为三个可组合片段，原 `confirm` 保留为薄同步包装（CLI `popper experiment confirm`、campaign_nodes、tests 仍可一次调用完成）：
  - `begin_confirmation(trusted_local, sandboxed)`：校验 + `_require_holdout_seal` + `BEGIN IMMEDIATE` + phase frozen→confirming + 提交 `test_consumed` 事件，返回已验证 state。后续 `evaluate(..., "test", ...)` / `_evaluate_via_worker(..., "test", ...)` 看到 phase=confirming 才接受 test split。
  - `finalize_confirmation(baseline, candidate)`：从已完成的 baseline/candidate 测试结果构造 claim 并落 completed；异常路径落 `confirmation_failed`（与原 `confirm` 同步路径 except 语义一致）。
  - `mark_confirmation_failed()`：幂等 best-effort 转移 confirming→confirmation_failed（用于 begin 之后、finalize 之前的异常兜底）。
- **`popper/research/controller.py` 新增 `_evaluate_via_worker(config, design_id, revision, split, sandboxed)`**：通用 Worker 评估路径，`split="test"` 时先 `_require_holdout_seal(sandboxed, "test")`，再用 `sandbox.sealed_reads([inside(project, spec["test"])])` 上下文管理器封住测试数据集——封读窗口覆盖整段 launch/poll/collect 循环，候选进程（Windows Low IL）在内核层被 EACCES 拒绝读测试集。原 `_evaluate_registered_via_worker` 退化为 dev 薄封装，调用 `_evaluate_via_worker(..., "dev", sandboxed=sandboxed)`。
- **`controller.confirm()` 去掉 914-921 阻塞 + 路由 revision 候选至 Worker**：定位 `selected_revision`——遍历 `run_dir/revisions/REV-*/revision.json`，若候选 dev observation 的 run_id 匹配 `RUN-<revision_id 摘要>` 则 `self.revisions.verify(revision_id)` 重算文件 SHA-256 与 manifest 摘要比对（任何篡改在这里失败，不带到 test 集执行）。然后 `confirm()` 改走：`begin_confirmation` → `evaluate(baseline, "test", ...)` + (`_evaluate_via_worker(candidate, "test", selected_revision)` if revision else `evaluate(candidate, "test", ...)`) → `finalize_confirmation`，异常走 `mark_confirmation_failed`。
- **`controller.implement()` 候选 dev run 同步写 `core.runs`**：此前 `implement` 只写 `store.runs`（research Run 表），`core.runs`（sqlite `.popper/state.db`）看不到候选 → `freeze()` 报「需要成功的基线和至少一个候选」。修复：`state = self._verify_inputs()` 后 `self.exp.register_run(config, "dev")`，独立评估算出 `evaluated["per_seed"]` 后 `exp.build_result(core_rid, core_state, config, "dev", per_seed, started, True)` + `complete_run`。`core.runs` 的 rid（uuid）独立于 controller 的 run_id（revision 摘要），通过 `config_hash` 关联，两者职责分明：core.runs 用于 freeze/confirm/replay 选 best candidate + 落核心 result；controller run_id 用于 research Run / budget / observations。
- **修掉 `except Exception:` 未绑定 `error` 的 bug**：原 `implement` 的 except 块 `type(error).__name__` 引用未绑定名，NameError 被内层 `try/except Exception: pass` 静默吞掉，`fail_run` 从未被调用 → core.runs 卡在 running，后续 `register_run` 以「已有运行中的实验」拒绝。改为 `except Exception as error:`。
- **测试**：`tests/test_research_workers.py::_exercise_revision` 加 baseline run（confirm 路径需要 baseline + candidate 都在 dev 跑过）、observation 数 1→2、预算 2→3，断言 `controller.confirm(sandboxed=True)` 推进 phase 至 `CONCLUDED`；`tests/test_research_confirmation_recovery.py` 两个 pre-consumption 失败测试改 patch `begin_confirmation`（原 patch `exp.confirm` 不再触发，因为控制器走拆分后的新方法）。回归 **586 passed / 1 skipped / 305 subtests**。
- **边界**：`sandbox.sealed_reads` 只在 Windows 强制完整性标签可用时成立；非 Windows 上 `--sandbox` 直接显式报错（发生在 `test_consumed` 提交之前，不白丢测试访问）。需要账户级/主机级隔离的正式确认仍应使用外部评估服务（`external_confirmation`）。
