## 三个不同的批准

1. **Study**：核对 `initial-answer.json` 的原始来源、模型、目标、候选、预测和反证条件，使用其明确的 `preview.approval_sha256` 批准。只建立 Study，不执行实验。
2. **Revision**：读取服务端 `preview-code` 的差异与对象版本，再使用对应 `proposal_sha256` 批准创建。只保存不可变 Agent 源码，不覆盖原冻结文件。
3. **执行/确认**：实验执行另外批准；独立确认还需冻结最终候选后再次单独批准。上面的批准不能作为执行批准，更不能作为确认批准。

```powershell
python -m popper.research.oscillator_campaign approve-study <正式目录> --run-id <ID> --approval-sha256 <核对后的 Study 摘要>
python -m popper.research.oscillator_campaign preview-code <正式目录> --run-id <ID>
python -m popper.research.oscillator_campaign approve-code <正式目录> --run-id <ID> --approval-sha256 <核对后的 Revision 提案摘要>
```

不要从 Agent 建议或自动脚本生成“用户批准”。独立确认不是本次实施任务中的默认操作。
运行中和成功的 Revision 不能走失败修复入口；修复绑定失败父版本，创建和执行仍分别批准，旧失败及预算消耗不清除。
单次组最多一个候选开发 Job；闭环组最多六个，排队、失败、取消均计入。重复排队同一不可变版本只返回原 Job。

## 报告口径

- 全局上限 60 次模型请求、400,000 tokens，不自动提高；所有工具续推理和人工重试也必须走同一账本。
- 两组共享初始材料、固定 RK4 代码与输出限制。单次组不得根据开发反馈修改方案；两组实际成本分别报告，不宣称预算消耗相同。
- 主条件是确认集轨迹误差相对下降至少 20%，闭环至少两次达到条件且失败率不高于对照。
- Kernel 的开发绝对阈值来自冻结 RK4 开发误差乘以 20%；这个换算不替代最终确认集的相对判据。Claim 或流程完成不是研究能力证据。
- Windows 读拒绝只证明指定参考与评分文件的隔离；无内核级断网，不宣称全宿主文件读取隔离或完全封闭环境。RHS 查询次数不等于所有算术运算成本。
- 尚未形成确认结果时，只能报告“模型提案待审批”，不能报告性能增益。真实失败、负结果、人工介入和未验证能力必须保留。
